# オーバーレイ付き映像の書き出し性能

2026-09-22調査。対象はv0.16.0と、インスタンス単位に準備範囲を限定する改善。実試合・個人情報を含む素材は使用していない。

## Hudl Sportscodeとの比較

[現行の公式更新履歴](https://www.hudl.com/releases/sportscode)では、12.74.0（2026-03-03）が既存映像との照合を改善してHudlへのアップロード時の再エンコードを回避し、12.73.0（2026-02-17）は描画を編集可能なレイヤーとして共有すると説明する。これは図形を焼き込んだ一般的なMP4の生成時間とは異なる。12.75.0はウィンドウサイズに依存しない高解像度のテキスト出力を説明する。

ローカルMP4へ同じ素材・解像度・描画を焼き込む現行版の秒数や比較ベンチマークは、今回の公式資料調査では確認できなかった。[2017年の「最大10倍高速化」](https://www.hudl.com/blog/new-ways-to-manage-your-video-with-sportscode)は当時の旧版との比較であり、現行版や本アプリとの速度比には使用しない。Sportscode実機での比較は未実施。

## 遅くなる箇所と今回の対応

v0.16.0では、同一ソースから選んだ最初の開始と最後の終了の間を一時生成する場合がある。前半・後半から6秒ずつ選択しただけでも、その間の不要なプレーや空白を処理し、さらに文字やPaintを重ねるため再圧縮する。

改善後はインスタンスごとに元ファイルを直接参照する。境界や欠落区間をまたぐインスタンスだけ、必要な範囲を準備する。主映像と副映像の時刻原点を別々に保持し、再生順・同期・Paintの時刻を変えない。同じ区間を異なるノートで使う場合も、最終出力は別々に描画する。

## 再現方法と評価範囲

`scripts/benchmark-overlay-export.mjs`で、同じ入力ディレクトリを使い、各ビルドに固有の出力ラベルを指定する。旧版の比較用worktreeにも同一のbenchmarkスクリプトを配置する。アプリ本体・Main・preloadを先にビルドし、計測中は他のビルドやテストを走らせない。既存の測定フォルダは上書きしない。

```bash
pnpm run e2e:prepare
node scripts/benchmark-overlay-export.mjs output/benchmarks/overlay-export baseline
# 改善版をビルド後、同じ合成素材を使用する
node scripts/benchmark-overlay-export.mjs output/benchmarks/overlay-export improved
```

合成素材は1280×720、30fpsの動くテストパターン（30秒、入力12Mbps）と48kHz音声。2つの元映像を共通時刻0秒・120秒に配置し、各6秒、合計12秒を選ぶ。比較用に1本のファイル内で6秒ずつ選ぶケースも含める。PaintはPNGの枠1つが移動する構成で、一般の追尾処理そのものは計測しない。

出力は両版とも同じH.264設定（macOSではVideoToolbox、5Mbps、yuv420p）を使用。起動画面が表示された後、12秒の文字付き出力を1回ウォームアップし、続く3シナリオについてIPC呼出しから保存完了までを計測する。SSIMは先頭6秒の上半分を入力の同時刻と比較し、文字・Paintのない画素の再圧縮差を見る。黄色いPaint枠が出力に見えることも画素で確認する。SSIMだけでは主観画質、HDR、10bit、音声、全描画の正しさを保証しない。

## 実測結果

Apple M2 / macOS 26.6.2。v0.16.0と改善版を交互に各3回実行した、ウォームアップ後の中央値（括弧内は最小〜最大）。いずれも合計12秒のMP4出力。Windows・4K・実試合での秒数は未測定。

| 条件                         |                 v0.16.0 |               改善版 |
| ---------------------------- | ----------------------: | -------------------: |
| 単一ファイル・文字           |    3.40秒（2.57〜3.44） | 3.14秒（2.46〜3.59） |
| 離れた2ファイル・文字        | 13.03秒（13.01〜13.30） | 3.81秒（2.95〜4.31） |
| 離れた2ファイル・文字＋Paint | 12.63秒（12.61〜13.93） | 4.04秒（3.22〜4.35） |

離れた2ファイルのケースでは中央値で文字付きが約3.4倍、文字＋Paintが約3.1倍速くなった。エンコードは3回から2回へ減り、126秒分の事前合成が不要になった。圧縮設定は変えていない。単一ファイルは生成処理の構成が同じで、今回の変更による明確な高速化は確認できない。

変更領域外のSSIMは、文字付きが0.999640→0.999744、文字＋Paintが0.999632→0.999741、単一ファイルは0.999744のまま。3回とも同じ値だった。この素材・領域では画質指標が悪化しておらず、中間圧縮を省いた分が改善している。出力の1280×720・30fps・12秒、Paint枠の表示も確認した。

各試行は`warm-baseline-1`〜`3` / `warm-optimized-1`〜`3`。測定結果は`output/benchmarks/overlay-export/<label>/results.json`へ保存し、映像・実行profile・生ログは公開しない。

参考として、ウォームアップを入れない予備計測（各3回、`final-baseline-*` / `final-optimized-*`）では、文字付きの単一ファイル出力の中央値が2.69秒→4.12秒だった。離れた2ファイルでは文字付き12.61秒→2.71秒、文字＋Paintで12.28秒→3.02秒。単一ファイルのケースはエンコード回数・入力・圧縮設定が同じであり、初回処理と定常処理を混ぜて全条件の高速化とは判断しない。

## 回帰検証

`pnpm run verify`が成功（190 files / 612 tests、型・Lint・アーキテクチャ・Design System・ADR検査、アプリ・Storybook build）。Main・preloadのビルドと検査後、macOSで`export-fast` / `export-menu` / `paint-export` / `multi-clip-playback` / `angle-sync-gaps` / `export-progress`の6つの実Electron E2Eが成功した。出力順、実際の文字・Paint描画、静止挿入、音声、複数アングルの時計、黒画面区間、進捗を確認した。

## 品質を優先した次の候補

1. 境界をまたぐ1インスタンスも、素材の連結と描画を一つのフィルター処理へまとめる。中間圧縮を減らせるが、複数アングル・異なるfps・無音・フリーズの時計を一緒に検証する必要がある。
2. 同じ素材・ノート・Paintを再出力する際の完成クリップキャッシュ。元映像の更新、フォント、描画と同期の変更で必ず無効化できることを採用条件とする。
3. ハードウェアデコードや描画処理の並行化は実測してから採用する。Macは既にハードウェアエンコードを使用している。[FFmpeg公式資料](https://ffmpeg.org/ffmpeg.html#Advanced-Video-options)もGPU・CPU間の転送でデコード加速が遅くなる場合を説明しており、単純に有効化すれば速くなるとは限らない。

現在のmacOS・Windowsの5Mbps固定設定は、元映像と同等の品質をすべての解像度で保証するものではない。画質方針を改善する場合は、元映像の解像度・fps・ビット深度と実画像の比較を基準に別途評価し、高速化のためにビットレートを下げない。

[FFmpegのstreamcopy仕様](https://ffmpeg.org/ffmpeg.html#Streamcopy)のとおり、圧縮データをコピーするだけなら高速かつ無劣化だが、文字や図形を焼き込むフィルターとは併用できない。元映像と完全同一の保持が必要な共有には、元映像と描画データを分けたパッケージが適する。今回、共有サーバーや新しい配布形式は導入していない。
