# パッケージ互換・原本保護・Sportscode XML取り込み

## 対応範囲

拡張子だけで互換性を決めません。読み込み前に設定・Timeline・映像参照を検証します。`.stpkg`はディレクトリ型です。

| 入力                                                              | 判定と結果                                                                                                                       |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 現行 `.stpkg`                                                     | 設定の`packageFormatVersion`未指定または1、`timeline.json`のversion 2、既知のアングル/クリップ構造を確認して開く                 |
| 旧 SporTag `.stpkg` / 拡張子なしのフォルダ                        | 旧Timeline配列、`tightViewPath` / `wideViewPath`、または映像参照のみの旧アングルを識別し、更新前の原本をバックアップへ保持し、元の場所・名前で更新 |
| 不明な設定version・Timeline version・不正時刻・重複ID・壊れたJSON | 推測で補修せず拒否。原本を保持                                                                                                   |
| 存在しない映像・範囲外の相対参照・symlink                         | 読み込みまたはコピーを拒否。外部の絶対参照は完全なパスを維持し、同名ファイルへ置き換えない                                       |
| Sportscode XML + 明示的に選択したローカル映像                     | 下記の専用操作で別の新規`.stpkg`を作成                                                                                           |
| Sportscode `.scpkg` / `.sczip`                                    | ネイティブ形式は未対応。拡張子変更や内部ファイルの推測では開かない。SportscodeからXMLを出力して使用する                          |

JSONは1ファイル16 MiBまでです。保存済みTimelineのclip数は共通の50,000上限に従い、新規映像導入Wizardの16ファイル上限と混同しません。旧構造の`actionType` / `actionResult`はType/Resultラベルへ移します。現行Timelineは行順・行色・空行と場面を持つversion 2です。groupの旧名称変換は旧配列入力だけに適用し、version 2とSportscode XML由来のラベルは名前・group・順序・重複を保持します。`actionType`と`Type`、`__proto__`と`constructor`も別の文字列として扱います。すべての歴代SporTag版・外部アプリ版の互換を保証するものではありません。

## 旧フォルダを安全に開く

1. 起動画面の共通の「パッケージを開く」からファイルまたはフォルダを選ぶ。保存形式は内容から自動判定する。
2. 以前に編集したコピーがあれば、その現在の内容を確認する。単一の有効な候補は自動採用し、分岐・不明時だけ使う内容を選ぶ。
3. 同じvolumeへコピーし、動画を含む全ファイルのバイトをSHA-256で照合する。権限・容量不足や取消では原本を置換しない。
4. コピーを変換・検証し、復旧journalを確定する。原本をバックアップへ退避してから、準備済み内容を元のパスへ設置する。以後の編集も元の場所へ保存する。

バックアップは日時とUUIDを含む隣接フォルダへ保存し、原本の全内容・復旧記録・手順を保持します。途中終了はOpenの最初に復旧し、無関係な同名ファイルや破損した復旧記録を上書きしません。個々のrenameは完成したフォルダを公開しますが、二段階全体が単一atomic exchangeではありません。電源断や外部アプリの任意の同時変更まで保証しません。

容量はコピー対象の総サイズ + 16 MiBを事前確認します。途中の容量変化や実割当量の差で失敗する場合も、原本または退避済みバックアップを保持します。詳しい候補選択、同一パス更新、復元手順は[移行仕様](legacy-package-migration.md)、設計上の制約は[ADR 0067](adr/0067-in-place-package-updates.md)を参照してください。

設定変換はMain内部のstagingにだけ適用し、旧configだけを書き換えるRenderer IPCは公開しません。

内部の絶対映像参照はコピー内の相対参照へ変換し、外部の絶対参照はそのまま保ちます。MainとRendererで同じ参照解決を使い、POSIX絶対パス・Windowsドライブ・UNC・正しいfile URIをパッケージパスへ二重連結しません。file URIの検索/fragment、encoded separator、不正なURLや未対応schemeは拒否します。異なるファイルをbasenameで探し当てる復旧はしません。外付けドライブが必要なら接続してから再試行してください。

## 読み込み・保存の失敗

Timelineの読み込みが成功して検証が完了するまで自動保存と文書変更を抑止します。読み込み失敗を空のTimelineとして保存しません。編集入口で履歴追加を止め、コードボタンとタグのホットキーも抑止します。再読み込みでは履歴と保留中のコード/ラベルを文書単位でリセットするため、空の文書へ失敗中の操作を持ち越しません。映像画面と独立Timelineにエラーを残し、「再読み込み」で原本からやり直せます。

保存失敗では画面上の変更を保持し、「保存を再試行」を表示します。権限、保存先、空き容量を直してから再試行してください。書き込み中にUndoして元の保存済み状態へ戻した場合も、その希望状態を後続書き込みとして保持します。保存はファイル単位で順番を守り、同じディレクトリの一時ファイルへ書き込み・sync・close後にrenameします。既存ファイルの書き込み権限を確認し、modeを維持します。WindowsのrenameがEPERM/EACCES/EBUSYで拒否された場合だけ、最大5回・追加375 msまで再試行します。権限を緩めたり、先に既存ファイルを削除したりしません。恒久的な拒否は保存エラーとして残します。一般のテキスト保存IPCとPlaylistの`playlist.json`置換もこの処理を使います。Playlistの映像処理全体をtransactionにする変更ではありません。

未保存の変更があるまま終了した場合の終了確認や、最後の300 ms debounceを必ずflushする処理はありません。保存失敗の表示が消える前に終了しないでください。原本保持と原子的なファイル置換は、停電時の耐久性・所有者/xattrの保持・全形式の保存成功を意味しません。

## Sportscode XMLから新規作成

1. Sportscode側でEdit List XMLを出力する。起動画面の「Sportscode XMLから作成」を開き、`.xml`を選ぶ。
2. 対応するローカル映像を明示的に1本選ぶ。`.mov` / `.mp4` / `.m4v` / `.webm`を受け付ける。
3. プロジェクト名、行/場面数、時刻範囲、警告を確認する。必要な秒数補正を入力する。開始と終了へ同じ秒数を加算する。
4. 映像と時刻・警告を確認したチェックを付け、保存先フォルダを選ぶ。取消では新規プロジェクトを作らない。
5. 映像をコピーして実尺を調べ、場面が映像の範囲に収まることを確認した後に新規`.stpkg`を完成させて開く。既存分析は置き換えない。

[Sportscode v10公式マニュアルのXML仕様](https://static.hudl.com/craft/SportsCodeManual-2.pdf)の`file / ALL_INSTANCES / ROWS`を基にした厳密なsubsetです。instanceの整数ID、秒単位の小数start/end、code、labelのtext/group、free_text、行名・順番・16bit RGB色を取り込みます。空行、同じ文字列でgroupが違うラベル、改行・日本語・emojiを保持します。欠けている行はcodeから導出します。XMLのescaped characterはdecodeします。

`SESSION_INFO/start_time`は表示用メタデータです。録画日時から秒補正を推測せず、前後半や動画の結合位置も推測しません。補正後の負時刻、終了<開始、24時間超、映像尺超過は拒否し、切り詰めません。DTD/ENTITY、namespace、scalar leafを含む属性（frame単位や未対応versionなど）、不正XML、重複IDや行名、不明な重要構造は拒否します。未対応の補助フィールドやsort指定は警告して、反映する値を確認します。旧Sportscodeが出す非標準・壊れたXMLを勝手に修復しません。

XMLのSHA-256、選択した映像名、秒数補正、警告を新しいコピーのメタデータへ記録します。完了直前にXML hashと映像のサイズ・mtime・inodeを再確認します。元XML・元映像・ネイティブSportscodeパッケージを変更せず、クラウドへ送りません。ネイティブパッケージ内部は新規保存先にできません。これはXMLの新規プロジェクト取り込みであり、Sportscodeの全機能やネイティブ形式の往復互換、XML出力、既存プロジェクトへのmergeではありません。

読み込み・作成失敗の説明はスクロール領域の外に残し、保存先選択の直前に確認できます。時刻の補正を変えた場合は、古いエラーと確認チェックを解除し、新しい補正を改めて確認します。

## ファイル選択と検証の限界

共通の「パッケージを開く」はmacOSでopenFile/openDirectory、WindowsでopenDirectoryを使います。拡張子filterで旧形式を隠さず、選択後の構造検証で対応形式か判定します。XML取り込み・新規作成の映像・保存先は目的別のダイアログです。取消や保存先フォルダを最近開いたプロジェクトへ登録しません。

合成データのunit/Electron回帰は[Testing](testing.md#パッケージ互換と保存保護)を参照してください。実Finder/Explorerの見た目、外付け実機、ACL、全歴代形式、Sportscode実機でのXML出力は自動テストだけでは確認できません。ローカルの実候補調査はメタデータと参照の存在確認のみとし、実データの移行・映像読込・外部uploadの証拠にはしません。


## 開くと再試行の状態

ドロップした単体映像はMainの内容検証後に新規作成へ案内し、接続障害と区別します。再試行は選択ダイアログへ戻ります。同期メタデータの更新も共通の原子的保存を使い、読み手へ空の途中JSONを見せません。空・不正JSON・非objectの設定を同期情報だけで置換しません。

選択 → 中断復旧 → 原本検証 → 以前の編集コピーの探索・必要時の内容選択 → stagingコピーと全バイト照合 → 変換・参照検証 → 原本とコピーの再確認 → journal確定 → 原本退避 → 元パスへ設置・検証 → バックアップ確定 → 文書読込 → 再生準備。

未確定stagingは開けません。失敗時は保存を開始せず、予約とbusyを解放します。登録先が未接続・破損している場合は再接続またはコピーの選択へ案内します。索引が失われたままコピーも移動すると初回と区別できないため、候補がない場合は共通Open内で一度だけ内容を確認します。形式を選ぶ質問ではありません。

現在の構造は拡張子がなくても再変換しません。Finderの`.DS_Store`更新は設置後の復旧判定に影響しません。0.17.9のコピーが後から編集された場合は内容の分岐を知らせ、自動で巻き戻しません。形式検証・コピーの同一性・映像のdecode成功は別々に検証します。
